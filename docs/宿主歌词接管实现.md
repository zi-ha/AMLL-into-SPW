# 宿主歌词接管实现（维护者文档）

> 面向对象：后续接手本项目的人，或宿主（Salt Player for Windows，下称 SPW）升级后需要重新适配的人。
> 对应实现：0.7.9 起稳定，0.8.0 完成加固；已用宿主 1.19.0（jpackage / Compose Desktop 1.12.x）验证。
> 本文只讲“怎么接到宿主歌词上”，歌词绘制与排版不在此范围。

---

## 0. 一句话原理

用 Workshop API 的 `replaceComposable` 接管宿主容器里**画歌词行的那个 Composable 调用**；在被接管的槽位里，用**反射把宿主原组件再执行一遍**，只把它参数里的 `Modifier` 换成 `Modifier.graphicsLayer { alpha = 0f }`，让整棵宿主子树照常组合、测量、跑副作用但不产出像素；然后**在同一个槽位**画我们自己的透明图层。

```
PlayerScreen
└─ PlayerLyrics (宿主)
   └─ LyricsContainer (宿主)
      └─ 行渲染 ھ.Ϳ  ← replaceComposable 接管这个调用点
         └─ [我们的 content]
            ├─ Box(宿主 Modifier)          ← 让宿主的 padding/尺寸只应用一次
            │  ├─ 宿主原组件(Modifier→alpha=0)   ← 反射调用，测量链不断
            │  └─ NativeLyricsContent            ← 我们的透明绘制层
```

---

## 1. 为什么必须是这个形状（约束推导）

Workshop API 只有三张牌，每张都缺一块：

| 手段 | 能做什么 | 缺什么 |
| --- | --- | --- |
| `hookRegistrar.replaceComposable` | 接管 Composable 调用点 | **没有 `original()`**，接管后原组件不再执行 |
| `hookRegistrar.hookMethod` | 有 `proceed`，能“执行原函数再改参数” | 宿主对 Composable 直接抛 `IllegalArgumentException: Use a Compose hook for androidx.compose.ui.ź.Ϳ`，此路对 Composable 永久封死 |
| `hookRegistrar.afterComposable` | 宿主一切照常，在后面追加一个兄弟节点 | 宿主文字仍在，必须用不透明层盖住 → 出现色块/接缝（用户明确拒绝） |

再看“能不能干脆替换掉”：

- 行渲染 `ھ` 不是单纯的绘制函数，内部是 `BoxWithConstraints` 子树，带 3 个 `LaunchedEffect`、`rememberCoroutineScope`、`derivedStateOf`，并向上报尺寸。
- 播放页左半屏背景面板的尺寸就取自这棵子树。
- 一旦把调用替换成空 lambda 或一个 `Box(fillMaxSize)`，**测量链和副作用就没了**；页面只在切歌过渡时重测这一列，于是表现为“快速切歌偶发塌成封面大小的方块”。

结论：必须“**宿主代码照跑 + 只让像素不输出**”。而要执行宿主原函数，只可能在自己的 Compose hook 里**反射调用**——这就是当前方案的全部理由。

## 2. 先勘察宿主（宿主升级后从这一步开始）

### 2.1 真正的代码归档不是 jar

SPW 由 jpackage 打包，安装目录（Steam 版）：

```
...\steamapps\common\Salt Player for Windows\
├─ app\
│  ├─ Salt Player for Windows.cfg      ← app.classpath=$APPDIR\ffmpeg-x64.dll
│  ├─ ffmpeg-x64.dll                   ← 名字是 dll，其实是 jar(zip)，所有应用类在这里
│  ├─ voxzen.aot                       ← -XX:AOTCache，不是 jar，别试图解压
│  └─ resources\
└─ runtime\lib\modules                 ← 只有 JDK 模块，没有应用类
```

读 `.cfg` 确认 `app.classpath`；这个名字每个版本可能不同，**永远以 cfg 为准**，不要硬编码 `ffmpeg-x64.dll`。

导出任意宿主类（开发机自用，不进插件）：

```python
import zipfile, os
p = r"D:\...\Salt Player for Windows\app\ffmpeg-x64.dll"
z = zipfile.ZipFile(p)
name = "androidx/compose/ui/ź.class"          # 换成要看的类
os.makedirs("out", exist_ok=True)
open("out/T.class", "wb").write(z.read(name))
```

反汇编（JDK 自带 javap 即可，注意 UTF-8 输出，宿主类名是各种 Unicode 字符）：

```bash
javap -J-Dstdout.encoding=UTF-8 -J-Dfile.encoding=UTF-8 -c -p out/T.class > t.txt
```

### 2.2 1.19.0 的实际名字（仅用于人工核对，代码里绝不写死）

| 逻辑角色 | 运行时类名 | 说明 |
| --- | --- | --- |
| `PlayerLyrics` | `androidx.compose.ui.ɻ` | 播放页的歌词入口，参数 `(Modifier, boolean, …)` |
| `LyricsContainer` | `androidx.compose.ui.ź` | 歌词容器，10 个业务参数 |
| 行渲染 | `androidx.compose.ui.ھ`，方法 `Ϳ` | 容器内唯一画歌词行的调用 |

R8 每个版本都会重新分配这些单字符名字，**升级后必然变化**。

### 2.3 靠编译器标记定位，不靠名字

Kotlin 编译器会把源文件名写进 class 常量池，宿主没有混淆这个字符串：

- `com.xuncorp.voxzen.ui.player.component.lyrics.PlayerLyrics (PlayerLyrics.kt:`
- `com.xuncorp.spc.lyrics.component.LyricsContainer (LyricsContrainer.kt:` ← 宿主原文就拼错成 `Contrainer`，别“修正”它

用 ISO-8859-1 读 class 字节直接 `contains` 即可（见 `NativeLyricsTarget.discover`）。

## 3. 定位算法

### 3.1 第一步：`NativeLyricsTarget.discover()`

在带 `PlayerLyrics.kt` 标记的类里，找“调用容器类”的那条指令，条件：

| 条件 | 原因 |
| --- | --- |
| `owner` 属于带 `LyricsContrainer.kt` 标记的类集合 | 只认容器 |
| 参数表中存在 `androidx.compose.runtime.Composer` | Composable |
| 业务参数（Composer 之前的部分）中恰好 1 个 `androidx.compose.ui.Modifier` | 布局 modifier |
| 业务参数中至少 2 个 `kotlin.jvm.functions.Function0` | 两个回调（跳转/点击等） |
| 返回 `void` | Composable |
| 调用前一条指令是 `ICONST_0` | **default mask = 0**，说明所有参数都显式传入，没有省略参数；有省略参数就无法安全替换 |

> 0.8.0 起不再断言“Composer 在第 10 位”或“第 4 个参数是 Modifier”。宿主增删参数时形状仍然成立，只有“两个 `Function0` + 一个 `Modifier`”这类结构才是真正必须的。1.19.0 上验证：全库命中 1 处（`ź.Ϳ`，2 个 `Function0`、1 个 `Modifier`、10 个业务参数）。

再用 `@kotlin.Metadata` 的 `d2` 数组校验时钟回调顺序：`onLineTime` 必须出现在 `onTime` 之前，且都在 `onClick` 之前——这是绑定播放进度的前提，顺序变了会静默错位，所以直接拒绝启动。

失败时的报错（可作为排查入口）：

- `宿主代码不是可读取的 JAR，无法确认原生歌词入口`
- `无法确认 PlayerLyrics → LyricsContainer 调用；以下调用使用了省略参数，无法安全替换：…`
- `无法唯一确认 PlayerLyrics → LyricsContainer 调用（找到 N 个：…）`（会列出每个候选的完整签名）
- `宿主歌词时钟参数顺序发生变化，无法安全绑定播放进度`

### 3.2 第二步：`NativeLyricsTarget.renderer()`

扫容器类（含编译器提取的 lambda 类）里所有方法调用，形状满足：

```kotlin
返回 void
参数表中存在 Composer，取它之前的“业务参数”
business 中恰好 1 个 com.xuncorp.spc.lyrics.KaraokeCompatStrategy
business 中恰好 1 个 androidx.compose.ui.Modifier
owner != 容器自身
```

然后 `singleOrNull()`——**必须唯一**，否则返回 null，插件拒绝启动。

为什么用 `KaraokeCompatStrategy`：它是容器签名里唯一没被 R8 改名的宿主类型；而 `MultiLyricsStyle` 运行时叫 `androidx.compose.ui.ž`，不能用来匹配。

## 4. 接管与反射调用

### 4.1 注册 hook

```kotlin
handle = WorkshopApi.hookRegistrar.replaceComposable(
    renderer.owner,      // 被调用方（行渲染类）
    renderer.method,     // 方法名
    target.owner,        // 在哪个类里替换这个调用（容器）
    renderer.parameters  // 只写业务参数，Composer/int/int 由框架追加
) { call -> HostLyricsPassthrough(call, renderer, original, created) }
```

`replaceComposable` 的语义（API 注释）：替换 `inClass` 内唯一的该 Composable 调用；扫描整个类，包括编译器提取的 lambda；**参数类型只包含业务参数**；同一位置多插件注册时优先级高者生效。

### 4.2 解析原方法：`Renderer.reflective()`

```kotlin
fun reflective(): java.lang.reflect.Method? = runCatching {
    val loader = WorkshopApi::class.java.classLoader          // 宿主 ClassLoader
    val types = parameters.map { name ->
        when (name) {                                          // 基本类型必须用 TYPE
            "boolean" -> java.lang.Boolean.TYPE
            "int" -> java.lang.Integer.TYPE
            // …byte/char/short/long/float/double 同理
            else -> Class.forName(name, false, loader)
        }
    } + listOf(
        androidx.compose.runtime.Composer::class.java,         // $composer
        java.lang.Integer.TYPE,                                // $changed
        java.lang.Integer.TYPE                                 // $default
    )
    Class.forName(owner, false, loader)
        .getDeclaredMethod(method, *types.toTypedArray())
        .apply { isAccessible = true }
}.getOrElse { error ->
    System.err.println("AMLL: 无法反射解析 $owner#$method：${error.javaClass.simpleName}: ${error.message}")
    null
}
```

要点：

- 用 `WorkshopApi` 的 ClassLoader —— 插件与宿主同进程，但插件自己的 ClassLoader 看不到宿主混淆类。
- `false` 表示不初始化类，避免在解析阶段触发宿主静态初始化。
- `setAccessible(true)` 在 classpath（非 JPMS 命名模块）场景不会被模块系统拦。
- **0.8.0 起在 `AmllPlugin.start()` 里解析一次**，成功后才注册 hook；失败直接拒绝启动（宿主继续显示原生歌词，页面正常）。因此 `HostLyricsPassthrough` 收到的 `Method` 一定非空，替换槽位不可能出现“什么都不画”。
- 解析失败会向 stderr 打一行 `无法反射解析 …`，宿主不打印插件栈时也能看到具体入口。

### 4.3 调用：`HostLyricsPassthrough`

```kotlin
@OptIn(InternalComposeApi::class)
@Composable
internal fun HostLyricsPassthrough(
    call: UiHookCall,
    renderer: Renderer,
    original: Method,          // start() 里解析，保证非空
    runtime: AmllRuntime,
) {
    val index = renderer.parameters.indexOf(Modifier::class.java.name)
    val hostModifier = if (index >= 0) call.arguments.getOrNull(index) as? Modifier ?: Modifier else Modifier

    Box(hostModifier.fillMaxSize()) {           // 宿主的 Modifier 只在这里应用一次
        val arguments = ArrayList<Any?>(call.arguments.size + 3)
        arguments.addAll(call.arguments)
        if (index in arguments.indices) arguments[index] = Invisible   // Modifier.graphicsLayer { alpha = 0f }
        arguments += currentComposer                                 // $composer
        arguments += -1                                              // $changed
        arguments += 0                                               // $default
        runCatching { original.invoke(null, *arguments.toTypedArray()) }
            .onFailure { DrawFailure.report(it, "宿主透传") }
        NativeLyricsContent(runtime, Modifier, true)                 // 我们的层
    }
}
```

三个追加参数的含义（这是 Kotlin Compose 编译产物约定）：

- `currentComposer`：当前组合的 `Composer`。`androidx.compose.runtime.currentComposer` 是 `@InternalComposeApi`，需要 opt-in；宿主升级 Compose 时要复核它是否还存在。
- `$changed = -1`：所有位都置 1，等价于“每个参数都视为已变化”。不能用 0，否则宿主会认为参数未变而跳过重组。
- `$default = 0`：全部参数都是显式传入，没有走默认值。前提是 §3.1 已校验 `ICONST_0`。

`Box(hostModifier.fillMaxSize())` 是必需的：宿主的 Modifier 里含容器的 `padding`，如果同时给 Box 和原组件，padding 会叠加两次，整列会偏移。

## 5. 绝对不能做的事（全部踩过）

1. **不要把行渲染替换成空 lambda 或纯 `Box(fillMaxSize)`**
   测量链会断，切歌过渡时左半屏背景塌成封面大小的方块。`fillMaxSize` 只是“看起来占了位”，宿主的 `BoxWithConstraints` 没有执行，尺寸贡献仍然是 0。

2. **不要用 `afterComposable` 叠加再盖一层不透明底色**
   宿主一切正常，但为了遮住原生文字必须画不透明层，结果是半宽矩形色块或放大封面，与整页渐变割裂。

3. **不要用 `hookMethod` 改 Composable 的参数**
   宿主会抛 `Use a Compose hook for androidx.compose.ui.ź.Ϳ`。这不是参数写错，是设计上禁止。

4. **不要把节流/静默信号挂在会被重建的 Composable 上**
   0.7.8 的“快速切歌静默期”把 `mark()` 放在 hook content 的 `LaunchedEffect(trackKey)` 里，content 每次重组都可能重启它 → 静默窗口无限延长 → 歌词永久不画。任何“跳过绘制”的分支都必须有“一定会结束”的保证，最好根本不要有。

5. **不要用一个 `DisposableEffect` 管理生命周期不同的 Skia 对象**
   `remember(measurer) { Painter(measurer) }` 会重建，共享 effect 的 key 变化时会把仍在使用的另一个对象一起 `close()`，随后抛 `Object already closed: Paint`——它发生在 `applyChanges` 阶段，会毁掉整次组合，绘制层的 try/catch 拦不住。

6. **不要在每一帧重排整篇歌词**
   宽度用精确相等判断时，切歌过渡的亚像素抖动会触发全量重排（80 行 × 每行多次 measure + 逐字包围盒），主线程被占满 → 只画出半帧。用 `LayoutBudget` 的阈值（宽度 1.2% 且 6px、字号 0.6sp）过滤。

7. **不要在 `onDispose` 里直接 close 仍在被渲染线程使用的 Skia 对象**
   用 `SkiaRetire.retire(...)` 延迟 2 秒后台回收；三个 Painter 的 `close()` 同时保持幂等。

## 6. 宿主升级后的排查流程

### Step 1 看插件是否启动

启动失败会抛出明确文案，先按 §3.1 的报错分类：

| 报错 | 含义 | 处理 |
| --- | --- | --- |
| `无法定位宿主歌词行渲染组件…` | `renderer()` 返回 null（形状不唯一/不存在） | 按 Step 2 重新勘察容器类 |
| `无法反射定位宿主歌词组件 …#…` | `reflective()` 解析不到原方法（参数类型对不上） | 按 Step 3 核对实际描述符；stderr 会打出具体原因 |
| `无法确认 PlayerLyrics → LyricsContainer 调用；以下调用使用了省略参数…` | 命中了容器调用，但调用点用了默认参数 | 见 Step 3 末尾的说明 |
| `无法唯一确认 PlayerLyrics → LyricsContainer 调用（找到 N 个：…）` | 形状命中多处 | 按括号里的签名加强区分条件 |
| `宿主歌词时钟参数顺序发生变化…` | Kotlin metadata 里 `onLineTime/onTime` 顺序变了 | 重新确认进度参数索引，更新校验 |

### Step 2 重新确认容器内调用（renderer 失效时）

```bash
# 1) 用 2.1 的脚本导出容器类（类名从上游 discover 的报错或日志里拿，或按 source 标记重新扫一遍）
# 2) 反汇编并列出所有带 Composer 的方法调用
javap -J-Dstdout.encoding=UTF-8 -J-Dfile.encoding=UTF-8 -c -p out/T.class > c.txt
grep -E "// (Method|InterfaceMethod)" c.txt | grep "Composer;" | sort -u
```

找“业务参数里同时有 `KaraokeCompatStrategy` 和 `Modifier`”的那一条，核对它是否仍是容器内唯一。如果变成多个，说明容器新增了别的歌词绘制路径，需要加更强的区分条件（例如要求参数中含 `LyricsDocument` 或某个 callback 形状）。

### Step 3 重新确认 `discover()`（容器签名变化时）

```bash
grep -n "LyricsContainer\|ź.Ϳ" c.txt        # 找到 PlayerLyrics 里调用容器的那一行
```

对照 `Type.getArgumentTypes(descriptor)` 打印出的实际参数，核对三个必要条件是否仍成立：

- 业务参数里**恰好 1 个** `androidx.compose.ui.Modifier`
- 业务参数里**至少 2 个** `kotlin.jvm.functions.Function0`
- 返回 `void`

0.8.0 起没有写死的参数索引，宿主增删参数不会导致定位失败；真正会失败的是“调用点使用了省略参数”（`$default` mask 不为 0）。这种情况 `discover()` 会把候选签名写进报错，但**无法安全替换**——替换一个带默认参数的调用，等于强行改变省略参数的取值。此时只能改为定位更外层（`PlayerLyrics` 本身），或者等宿主 API 提供 `original()`。

### Step 4 验证反射是否成功

启动时已经会向 stderr 打一行；若在调试环境看不到，可临时在 `AmllPlugin.start()` 里加：

```kotlin
System.err.println("AMLL: renderer=${renderer.owner}#${renderer.method} original=${original != null}")
```

- `original != null` → 反射解析成功（0.8.0 起这是启动的必要条件，否则直接报错）；
- `original == null` → 不会发生，`start()` 已经 `error(...)`；若真出现，说明有人改动了这层校验。

排查签名对不上时，重点看业务参数里是否有**基本类型**（`boolean/int/…` 必须用 `TYPE` 而不是 `Class.forName`）。数组参数由 `typeOf()` 递归处理（`java.lang.String[]` → `String[].class`），嵌套数组同样适用。

### Step 5 回归清单

- 冷启动进播放页，歌词立即出现（不延迟、不空白）
- 连点「下一首」10 次以上；上一首/下一首交替乱点
- 自然播完自动切歌
- 暂停再播；拖动进度
- 切到无时间轴的纯文本歌词（容器走空状态分支）
- 纯音乐页面（诗词分支）
- 关闭插件再启用；切换主题/全屏
- 观察 `%USERPROFILE%\.amll-spw-draw.txt` 是否出现（出现即有绘制异常）

## 7. 代码地图

| 文件 | 职责 |
| --- | --- |
| `host/AmllPlugin.kt` | 插件入口：权限检查 → `discover()` → `renderer()` → `reflective()` → 注册 `replaceComposable` → 起运行时与 TTML/底栏桥 |
| `host/NativeLyricsTarget.kt` | 运行时用 ASM 扫宿主归档：`discover()` 找容器调用点，`renderer()` 找行渲染，`Renderer.reflective()` 解析原方法 |
| `host/HostLyricsPassthrough.kt` | 接管槽位的实现：反射执行原组件（alpha=0）+ 画我们的层 |
| `host/NativeLyricsContent.kt` | 宿主适配层：`collectAsState` 取呈现状态与偏好，转成绘制层要的参数 |
| `host/NativeLyricsArguments.kt` | 历史遗留：从 `UiHookCall.arguments` 里按参数名取 `Modifier`；当前 `HostLyricsPassthrough` 已内联等价逻辑，此文件未被调用 |
| `ui/AmllLyrics.kt` | 绘制入口 `NativeLyricsSurface`：布局缓存、Skia 画布隔离、帧驱动 |
| `ui/LyricsScene.kt` | 呈现状态之间的过渡（当前替换槽位里**不使用**，避免双层尺寸动画） |
| `ui/FrameBudget.kt` | `LayoutBudget`：宽度/字号漂移阈值，抑制过渡期间的全量重排 |
| `ui/SkiaRetire.kt` | Skia 原生对象延迟回收（2s 宽限 + daemon 线程） |
| `ui/DrawFailure.kt` | 绘制异常去重并落盘 `%USERPROFILE%\.amll-spw-draw.txt` |
